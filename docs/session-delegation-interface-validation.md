# 跨会话委派接口验证

本文记录正式接入前的 P0 阶段证据，不作为当前部署能力或待办状态的权威入口。后续接入已完成，当前契约见 [委派说明](session-delegation.md)，当前验证见 [验收说明](acceptance.md)；下文“下一阶段”“尚未”等表述均指本阶段当时。

验证日期：2026-10-22。范围为隔离会话的接口可行性，不包含正式微信委派功能开发。

后续正式接入已经实现并加载本机中间件，见[微信跨会话委派](session-delegation.md)。下文保留接口验证的范围和证据，不代表当前仍停留在 P0。

## 结论

**后续验证已打通独立中间件到已有 Desktop 会话的发送、执行和结果回传。** 路径为独立中间件 App Server 的正常模型回合 → 官方 bundled `codex_app` MCP → `send_message_to_thread` → Desktop 目标会话执行 → `wait_threads` → 中间件原会话最终回复。中间件不接管 Desktop 写入权，也不借用当前人工聊天身份。

这是 P0 接口通道通过，不等于正式微信委派功能已经上线。现有微信服务没有改配置或重启，归属授权、持久化委派记录、排队、附件和微信自动交付仍需接入。

## 已定位的接入条件

- 正常中间件模型回合必须先取得属于自身实例的 Guard 租约。简单探针只设置 Bridge 环境标记、没有租约时，Hook 会正确拦截，甚至可能出现回合 completed 但没有最终回复；不能把 completed 单独当作任务成功。
- 官方 Desktop 工具需要实际调用上下文。同一临时配置在未运行真实回合时直接 RPC 调用失败；正常模型回合调用成功，此后直接只读调用也成功。该对照支持执行上下文初始化的必要性，未证明内部所有校验细节。
- 工具配置与本轮审批策略必须一致。临时自定义 MCP 缺少工具许可时，正常回合明确报 `MCP tool call requires approval, but approval policy is never`。验收仅对用户已明确授权的三个工具配置许可，不修改全局 MCP、插件信任或审批策略。
- 官方 bundled MCP 的命令、工具限制和 Desktop 提供的连接环境需要显式传入。配置只在隔离进程中生效；不能把默认 disabled 改成永久全局开放来替代通道归属设计。

## 可重复运行的 P0 验收

仓库脚本 `scripts/verify-desktop-delegation.mjs` 从 Desktop 提供的进程环境运行，显式指定已授权的隔离目标：

```powershell
node --disable-warning=ExperimentalWarning --experimental-strip-types scripts/verify-desktop-delegation.mjs --target <隔离测试会话ID>
```

目标必须包含准备标记 `DESKTOP_TARGET_READY`；脚本不会新建或接管业务目标。每次使用新的委派标记和独立租约库，发送一次计算及文件写入/回读任务，只允许目标操作其工作目录 `outputs/` 中以本次 UUID 命名的新文本文件。脚本核对工具发送次数、精确目标、等待回执、目标完成回合、原会话回传结果及磁盘文件内容。协议证据只保存到忽略的 `.local/delegation-acceptance/`，不记录桌面连接地址；标记文件保留在隔离目标目录，不删除历史。失败不能直接重发原任务，应先查看原始目标是否已经执行。

脚本实机运行已返回 `passed=true`、`singleSend=true`、`guardLeaseUsed=true`、`fileProofVerified=true`。脚本语法及 `git diff --check` 通过。本轮只新增验收脚本和文档，未修改正式业务源码，没有重新宣称执行全量源码测试。

脚本依赖 Desktop 官方工具包和当前可用的 `CODEX_APP_TOOLS_PIPE_PATH` 环境；缺少环境时明确失败，不硬编码地址、不伪造调用身份。Windows 登录计划任务没有天然继承当前 Desktop 的进程环境，因此常驻服务如何获取、刷新并校验连接仍是正式接入门槛，尚未以本次成功替代开机/应用重启恢复验收。

测试任务只计算数字和回复标记，没有调用业务工具、修改业务文件或联系其他业务会话。临时 MCP 配置只用于独立测试进程，没有修改全局配置或现有中间件部署。服务未停止或重启，Windows 未重启；结束检查原中间件 PID 保持不变，两个微信通道运行中。隔离测试会话保留，便于核对，不删除历史。原始接口证据位于忽略的本机 `.local/` 中，不随仓库提交。

## 对设计的调整

1. 把 Desktop 持有的会话投递与中间件自己持有的会话执行分为两条路径。不能统一用独立 App Server 的 resume/start 处理所有目标。
2. Desktop 目标通过官方工具投递已经验证。下一阶段需将上述执行上下文与受限工具配置接入实际通道，并解决登录计划任务与 Desktop 环境之间的连接发现、刷新；不能伪造调用会话身份、借用当前人工聊天身份或固化本次桌面连接地址来冒充稳定集成。
3. 尚未打通时，明确返回“目标由 Desktop 持有，当前投递通道不可用”，保持目标运行；不要自动 fork 成另一个会话后谎称已发给原目标。
4. 结果回收可以复用只读观察通道；用目标回合编号、委派编号和最终状态匹配，不能只抓最新一条回复。轮询等待不等于目标主动反向发消息；中间件负责可靠回传更容易恢复。
5. 待投递路径通过后，再实现持久化委派记录、归属授权、同名消歧、忙碌排队、失败去重、附件和微信结果交付。

本次未验证忙碌会话排队、审批转发、附件回传、服务/应用重启恢复，也没有验证目标主动调用反向消息工具。暂不将这些列为已支持。

接口概念参考 [OpenAI App Server 文档](https://learn.chatgpt.com/docs/app-server)。实际可用性以上述本机接口验证为准。
