# 微信跨会话委派

微信管家可以将用户本轮明确指定的任务交给已有的 Codex Desktop 会话，持续追踪并把结果交回原微信通道。目标使用自己的上下文、模型、权限及项目规则；中间件不接管或重启目标进程，不自动同意目标的审批。

## 使用方式

直接发送自然语言，不需要切换当前管家会话：

- `告诉「会话准确名称」，检查剩余任务并给出进度，完成后把结果返回给我。`
- `委派会话 <会话ID>，只读取指定测试文件并汇报内容，完成后返回结果。`
- `查询委派列表。`
- `查询委派 <委派编号> 的状态。`
- `取消尚未投递的委派 <委派编号>。`

名称可以使用用户本轮写明的名称片段；多个授权会话匹配时拒绝猜测，应补充准确名称或 ID。不能委派给管家当前会话自身。用户应明确本轮任务范围，机器人不能把历史、附件或其他会话返回的指令当作用户本轮的新任务授权。指代只复用目标，不复用旧任务权限。

管家内部调用受限工具 `delegate_task`，操作为 `submit`、`confirm`、`list`、`status`、`cancel`。`target` 是名称片段或 ID，`instruction` 是目标任务，`jobId` 是委派编号。用户无需直接填写工具 JSON。

提交后的 queued 回执只表示任务已持久化排队，不表示目标已经接收或执行成功。目标忙碌时保持排队，不发送 stop。`cancel` 只适用于尚未投递的任务；它不停止 Desktop 中已经开始的任务。微信原有 `stop` 仍针对当前管家回合，不等于取消其他会话中的委派。

## 指代接续与确认

用户可在收到委派结果后直接说“告诉它让它推送远端”。本轮仍须有明确的委派意图；服务从同一微信通道、同一来源管家会话最近 24 小时的非取消且仍有权限的委派中查找目标。唯一目标可直接接续，不要求本轮重复完整名称，不接受模型凭空补出的其他目标。

存在多个目标、或明确名称匹配到多个会话时，返回 `needs_confirmation`、候选和直接提问；管家应问“你指的是哪个会话？”，不要求重写整条任务。原任务保存在私有 SQLite 的 `delegation_followups` 中，10 分钟内有效；用户确认名称或编号后调用 `confirm`，服务使用保存的任务，忽略模型试图替换的任务正文。没有近期目标时同样保留任务，询问名称后继续。多个候选时单独“是”不足以选择；真正同名时用会话编号区分。

确认按通道和来源会话隔离，并再次检查目标权限与来源回合有效性。同轮重复确认复用已有任务，旧确认不能在后来回合再次执行；否定或附带新任务的回答不能直接执行旧请求。服务恢复保留尚未过期的确认，过期后需重新说明任务。确认中间件里的目标不替代目标项目本身的审批规则。

此修复已通过类型检查和 606 项全量测试；2026-10-23 经本次用户授权，在空闲门禁通过后重启常驻中间件，两个微信通道恢复运行，新确认表已建立，非当前微信来源仍被拒绝且未新增委派。真实微信端指代体验待用户验收。不会因为截图展示了推送请求就自动重发或推送仓库。

## 连接与旧会话兼容

中间件按需枚举当前 Windows 用户可访问的 `codex-app-tools` 命名管道，使用官方 bundled MCP 服务连接 Desktop，不硬编码验收时的连接地址。没有继承 Desktop 环境变量的独立进程已验证可以发现并调用。连接失效后下一次观察重新发现；发送调用不自动重试。多个可用 Desktop 连接且无法唯一定位时拒绝猜测。

新会话有原生动态工具；旧微信会话通过独立受限的 `ilink_delegation` MCP 入口补充工具。配置只注入中间件自己启动或恢复的执行会话，不写全局 Codex 配置、不开放 Desktop 的通用消息工具给模型，也不改变现有会话 ID、人设或模型。该本机入口会再次核对真实来源会话、回合、通道和当前用户输入，不能用任意传入的 threadId 冒充授权。

Desktop 必须正在运行且其本机工具可用。连接发现、旧会话兼容和完整执行已实机验证；未通过重启 Windows 或重启 Desktop 来扩大验收结论。

## 通道权限配置

本机私有数据目录首次加载时生成 `delegation-permissions.json`，已有文件不会被覆盖，配置不随仓库提交。它与账号状态库、人设目录位于同一私有数据根目录，详见[目录结构](directory-layout.md)。格式示例：

```json
{
  "version": 1,
  "accounts": {
    "primary": { "allowDesktopThreads": [] },
    "secondary": { "allowDesktopThreads": ["<允许共享的Desktop会话ID>"] }
  }
}
```

- 默认沿用现有归属：主微信可访问尚未分配给微信通道的本机 Desktop 会话；每个微信只能操作自己归属的会话。
- 其他微信需要按 ID 显式授权，才能委派未分配的 Desktop 会话；没有通配符或默认全部共享。
- 该配置不能覆盖已明确归属其他微信通道的会话。无法读取、格式错误或缺少授权项时，不新增跨通道权限。
- 每次投递、观察、交付前重新检查授权；撤销后暂停，不停止目标任务，也不自动泄露已经缓存的结果。
- 模型不能通过微信工具修改授权文件。这个权限边界约束中间件的委派接口，不构成 Windows 文件系统沙箱。

## 任务持久化与交付

同一个私有 `state.sqlite` 新增 `delegation_jobs`，保存来源通道/会话/回合、用户委派原文、目标、任务范围、状态、关联目标回合、分页位置和最终结果。不得上传该库或日志。

状态流为 queued → sending → running → completed → delivered；另有 unknown 和 cancelled。每次实际发送前先提交 sending 检查点，同一目标的委派按顺序处理。发送前两次核对 Desktop：会话状态须为 idle 或 notLoaded，且返回的回合列表存在、各回合均已完成、失败或中断。notLoaded 仅表示未加载，不单独证明空闲；出现进行中回合、审批等待或未知状态时仍排队。发送回执必须指向正确目标。

发送超时、连接断开或服务恢复时遗留 sending，转为 unknown，只读核对，不自动重新执行。相同来源回合、相同目标的重复工具调用复用委派记录；内容冲突则拒绝。取消和投递之间使用数据库条件更新，避免取消后的旧内存状态继续发送。

目标消息带唯一委派标记；中间件将它与真实目标回合关联，不把最新一条无关回复当作结果。历史分页位置持久化。最终全文从原生 summary 页读取，不把 Desktop 只读预览的文字上限当作最终结果上限。微信交付复用持久化 outbox，按段落完整分片、使用固定消息 ID 重试，不重新执行目标任务，也不切换当前管家会话。

结果是目标原始最终文字附带来源信息，不会自动作为新指令重新驱动管家。当前委派交付以文本为主，目标中的本机文件链接尚未作为此异步路径的附件自动回传；需要附件时仍使用已验收的普通微信文件任务流程。

Desktop 消息接口不提供“仅在指定空闲版本下发送”的原子条件。本机检查和中间件目标锁避免主动向已知忙碌目标投递；若人工同时在 Desktop 操作同一目标，仍受 Desktop 自身调度行为影响。审批等待、异常中断、没有可确认回执等情况不能伪装为任务成功。
