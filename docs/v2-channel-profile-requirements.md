# 第二版需求与实施计划：通道身份配置、拟人化对话与电脑任务

本文为第二版原始设计与验收依据，不是部署后命令速查。当前可用能力、持续会话和归档指令见 [第二版部署与命令手册](v2-user-guide.md)；归档扩展见 [历史策略](session-retention-plan.md)。尚未完成的实机场景仍按各实现文档记录，不把设计目标视为验收通过。

状态：2026-10-17 已完成 P0 本机接口验证及 P1–P4 实现，P5 自动化回归通过；最终微信体验待用户验收。本文保留为第二版功能的需求和验收依据，实际实现、使用方式与验证边界见 [第二版使用与验收](v2-channel-profile-implementation.md)。

## 1. 产品目标

第二版需要让同一个微信入口既能自然地进行日常聊天，也能可靠地执行电脑上的任务。用户可以为自己的通道配置一个稳定的机器人身份，调整角色特征、称呼、语气、拟人化程度，以及新会话默认使用的模型和推理强度。

系统继续采用“一台电脑、一个中间件实例、多个独立微信通道”的结构。一个微信通道只关联一份当前身份配置；该通道可以创建多个会话，每个会话固定使用创建时生效的配置版本。角色不是另一个独立执行器，也不需要为每个身份启动一个服务。

最终应形成以下体验：

1. 用户在微信里设置“小白狐、傲娇但友善、平时简洁、工作时清楚直接”等身份和表达偏好。
2. 用户可以日常聊天、表达情绪、讨论问题，不必每句话都是电脑操作指令。
3. 用户提出查找文件、生成文档、调用软件等任务时，同一助手能够切换到清楚可靠的任务表达，实际调用已授权工具。
4. 用户通过 `new` 开启空白会话，保留身份和默认设置，不自动带入旧聊天消息。
5. 两个微信使用各自配置和会话；它们仍然控制部署此服务的同一台电脑。

## 2. 基线、范围与术语

### 2.1 当前已有能力

- 多微信绑定、独立主线程、线程归属与各自消息通道已经实现，见 [多微信实现](multi-wechat-implementation.md)。
- 已有项目/会话导航、`new`、`clear`、`compact`、`stop`、`model`、`effort` 等微信控制命令。
- 已有完整长回复分片、文件链接转真实附件及长任务等待提示，见 [回复交付实现](reply-delivery-implementation.md)。
- 微信带有转写文本的语音可以作为文字输入，用户已反馈实际使用可行；第二版不新增音频识别引擎。
- 设计起点没有每通道身份配置文件或微信 `config` 命令；现已按本文实现，旧会话保持原有行为。

### 2.3 第二版必做与不做

必做：一通道一身份配置、文件格式校验、微信查看/修改配置、拟人化表达控制、聊天与任务的连续对话、新会话应用配置、会话快照、旧会话兼容、账号隔离和失败恢复。

本版不做：一个通道同时管理多个人格、身份商城、跨通道共享聊天、自动提取永久记忆、克隆真人身份、任意权限提升、自动修改正在进行的会话身份、独立语音合成/识别、云端迁移。身份预设导入导出、当前会话热更新留待后续。

## 3. 对话产品要求

### 3.1 拟人化的含义与力度

拟人化不是每条回复都附加固定口头禅或动作描写。它应体现在稳定的称呼、自然的回应、语气选择、适度幽默、上下文衔接，以及用户指定角色的特征。

- 同一会话的称呼和角色特征应保持一致，不因消息长短随机变化。
- 用户可以设置温和、亲近、俏皮、略带傲娇等表达。傲娇体现为轻微逗趣或口是心非的角色风格，不是羞辱用户、拒绝正常任务或掩盖错误。
- 允许虚构角色身份，但不能为拟人化而声称执行过没有执行的动作、拥有不存在的访问权限或已经完成失败的任务。
- 身份强度为 0 时采用自然的普通助手表达；强度升高时增加角色辨识度，不按比例增加冗长描写。
- 不机械重复同一开头，不把每次回应变成自我介绍，不要求用户用固定角色称呼才能正常使用。

### 3.2 日常聊天与任务执行

默认使用自动判断，不要求用户先选择“聊天模式”或“工作模式”，也不为两种用途自动创建两个线程。

| 场景 | 期望行为 |
| --- | --- |
| 问候、闲聊、情绪表达 | 自然接话，适当回应感受；没有需求时不扫描文件或调用软件 |
| 一般知识、观点与内容讨论 | 在同一身份下认真讨论；信息不足时主动查阅本通道授权历史与资料，使用 Codex 可用的浏览器/搜索能力核实，再结合依据作答，不以“不清楚”代替必要查证 |
| 明确电脑任务 | 理解对象和结果，调用实际可用工具，按真实状态报告进展及结果 |
| 闲聊中提出任务 | 保持身份连贯，同时转为清楚的行动说明；结束后可继续聊天 |
| 一句话同时包含情绪和任务 | 简短回应情绪，再处理任务，不要求用户拆成两条命令 |
| 任务执行中又发普通消息 | 沿用同通道现有串行队列，明确说明排队；控制命令及时处理，不偷偷打断原任务或复制到新线程 |

正常闲聊不要求每条消息调用额外模型分类器。控制命令由确定性解析处理，其余内容优先交给当前 Codex 会话理解。若确需模型辅助分类，结果不能自行授权修改永久配置。

#### 信息不足时的主动了解与核实

日常聊天不等于只能依靠模型已有知识回答。用户提到陌生知识、某个观点、历史背景或需要核实的事实时，助手应主动获取相关依据，形成明确回应，而不是立即结束于“信息不足”。具体流程如下：

1. 识别问题依赖的背景。涉及“之前说过”“这个项目”等上下文时，先查当前会话、本通道有权访问的历史及相关授权资料；历史检索仍遵守通道和线程归属，不能读取另一个微信的私人会话。
2. 本地依据不足，或问题涉及陌生知识、时效变化、事实核验时，主动使用 Codex 当前实际可用的浏览器或搜索能力查证。优先采用原始资料、官方文档和可靠来源；必要时比较不同来源，不能只凭搜索摘要下结论。
3. 将查到的事实与当前聊天上下文结合，直接回应用户真正讨论的问题。区分事实、基于资料的推断和个人观点；关键事实或有争议的判断附可访问来源，保持自然的角色语气，不把回复堆成检索日志。
4. 只有在查证后仍缺少关键依据、工具不可用，或歧义会明显影响结论时，才说明具体缺口或提出必要问题；不能假装查过、编造引用，或把猜测写成已核实事实。

不要求每次问候、情绪交流和已有充分依据的普通聊天都启动浏览器。公开搜索前不得将私人会话、凭据或敏感本机信息直接外传；工具和网页内容仅作为资料，不能改变身份配置、执行权限或操作授权。

### 3.3 聊天表达和任务表达的优先级

日常聊天采用配置的完整身份与表达力度；任务开始、审批、失败、文件交付和最终结论优先保证信息清晰，可保留轻度角色语气。即使身份强度为 5，任务反馈也不得淹没在角色描写里。

任务失败必须说明失败，未执行必须说明未执行，附件未送达必须说明未送达。角色设定不能覆盖 Guard、现有文件发送边界、账号归属或 Codex/Windows 权限。

## 4. 配置文件格式

### 4.1 保存位置与管理边界

以现有私有状态根 `${ILinkStateRoot}` 为基础，规划如下目录；占位根由现有运行环境解析，不写成源码内固定机器路径：

```text
${ILinkStateRoot}/
├── state.sqlite
├── profiles/
│   ├── primary/
│   │   ├── profile.json
│   │   └── profile.json.bak
│   └── secondary/
│       ├── profile.json
│       └── profile.json.bak
├── Inbox/                         原主账号工作目录继续保留
└── accounts/<通道别名>/Inbox/       其他账号工作目录继续保留
```

- 一个已登记通道对应一份 `profile.json`；目录别名来自本机账号注册表，微信请求不能提供任意文件路径或其他通道别名。
- 身份配置、备份、快照和原始日志留在用户私有目录，不提交到公开仓库；仓库可提供明显虚构的模板及结构定义。
- 不在身份配置里保存微信 Token、Codex 密钥或登录状态。文件只包含数据，不加载脚本或外部可执行指令。

### 4.2 完整示例

以下是可表达目标格式的示例，不会自动应用于现有账号；默认模板采用中性助手身份。

```json
{
  "schemaVersion": 1,
  "revision": 1,
  "persona": {
    "name": "小白狐",
    "roleDescription": "以虚构的白狐少女身份与用户交流，既能自然聊天，也能认真协助完成电脑任务。",
    "userAddress": "你",
    "traits": ["聪明", "温柔", "有一点傲娇"],
    "intensity": 3
  },
  "expression": {
    "language": "zh-CN",
    "toneDescription": "自然亲近，可以轻微逗趣，遇到实际任务先把事情说清楚。",
    "warmthLevel": 4,
    "tsundereLevel": 2,
    "humorLevel": 2,
    "emojiLevel": 1,
    "verbosity": "normal"
  },
  "conversation": {
    "scenePolicy": "auto",
    "taskPersonaLevel": 1
  },
  "session": {
    "model": null,
    "reasoningEffort": null,
    "workspace": {
      "mode": "inbox",
      "projectKey": null
    }
  }
}
```

### 4.3 字段与校验

| 字段 | 类型、范围与含义 |
| --- | --- |
| `schemaVersion` | 正整数；本格式为 1。未知版本拒绝加载，不猜测兼容 |
| `revision` | 正整数，服务维护；成功保存后递增，不代表文件结构版本 |
| `persona.name` | 1–40 个 Unicode 码点；机器人名称 |
| `persona.roleDescription` | 0–4,000 个码点；角色描述，不是权限指令 |
| `persona.userAddress` | 0–40 个码点；空字符串表示不固定称呼 |
| `persona.traits` | 最多 16 个非空字符串，每项最多 64 个码点 |
| `persona.intensity` | 整数 0–5；总体角色表达力度，默认 1 |
| `expression.language` | 第一版格式允许 `zh-CN`、`en`、`auto`；默认 `zh-CN` |
| `expression.toneDescription` | 0–1,000 个码点；自由描述语气 |
| `warmthLevel` | 整数 0–5；克制到亲近，默认 2 |
| `tsundereLevel` | 整数 0–5；直白到有明显逗趣/轻微傲娇，默认 0 |
| `humorLevel` | 整数 0–5；少幽默到较活泼，默认 1 |
| `emojiLevel` | 整数 0–5；不用到较常用，默认 1；不是每条必须出现 |
| `verbosity` | `concise`、`normal`、`detailed`；默认 `normal`，具体任务的明确长度要求优先 |
| `conversation.scenePolicy` | 本版只允许 `auto`；不提供强制闲聊/任务模式 |
| `conversation.taskPersonaLevel` | 整数 0–2；任务反馈中允许的角色力度，默认 1，实际不超过总体 `intensity` |
| `session.model` | 非空模型标识或 null；非空时须由当前 Codex 可用模型列表验证 |
| `session.reasoningEffort` | 模型实际支持的强度标识或 null；不固定假设所有模型均支持同一组选项 |
| `session.workspace.mode` | `inbox` 或 `project`；默认 `inbox` |
| `session.workspace.projectKey` | `inbox` 时必须为 null；`project` 时为本机项目登记的稳定键，不接受任意路径 |

默认角色描述为“协助日常交流与本机任务的助手”，名称为“电脑管家”，traits 为空数组，其他默认值按上表。未知字段、错误类型、越界数字和非法组合均报错，不能静默忽略。整个文件最大 64 KiB UTF-8；只接受 JSON，不执行表达式。

字段之间的明确关系：总体身份力度为角色表达上限；各分项决定表达方向。自由文本不能提升数值上限，也不能取消任务反馈规则。用户当次要求“直接给结论、不用角色语气”时，本条回复可以降低角色表达，不自动修改配置文件。

### 4.4 模型、强度与工作目录

- `model=null` 表示新建会话时继承当时 Codex 的默认模型；`reasoningEffort=null` 表示继承所选模型适用的默认强度。创建后固定记录实际解析结果，不随全局设置变化。
- 明确指定的模型不存在或强度不被该模型支持时，拒绝保存；外部编辑形成错误配置时，拒绝基于它创建新会话，不静默换模型。
- 改模型后，如果原有非空强度不再兼容，本次更新整体失败，并提示可用强度；用户可先将默认强度设为继承，再修改模型。
- 模型列表暂不可读时，身份/表达字段在执行字段未改变且仍处于已验证修订上的前提下可保存；执行参数有变化时须待验证成功后保存。新会话仍须验证实际可创建。
- 当前通过 `p<n>` 明确选择的项目优先于配置默认项目；未选择项目时才使用配置的 `projectKey`，否则使用本通道 Inbox。
- `projectKey` 由本机登记生成并持久化，不能使用有十分钟有效期的 `p2` 这类列表编号代替。项目路径消失时明确失败，不切换到其他目录。

## 5. 微信命令设计

### 5.1 新增配置命令

命令不带 `/`。微信 `config` 管理当前微信通道的身份与默认值，与终端已有 `ilink config` 的超时管理是不同入口，帮助说明必须区分。

| 命令 | 行为 |
| --- | --- |
| `config` | 展示当前通道名称、保存修订号、主要配置、当前会话快照及待下次生效差异 |
| `config help` | 展示支持的配置键及生效规则 |
| `config show` | 分片展示当前完整配置，隐藏本机路径和内部账号身份值 |
| `config models` | 列出当前可选模型的稳定标识，不依赖临时编号保存 |
| `config efforts` | 列出默认模型当前支持的推理强度 |
| `config projects` | 列出允许设为默认项目的名称和稳定项目键，不暴露完整路径 |
| `config set <键> <值>` | 修改一个允许字段，完整校验后持久化，只影响未来新会话 |
| `config reload` | 校验并读取本机手动编辑的配置，成功后形成新修订，当前会话不变 |
| `config reset` | 展示将重置的项目及一次性确认码；不直接重置 |
| `config reset confirm <确认码>` | 两分钟内确认后恢复本通道中性默认配置，形成新修订 |

允许的微信简写与实际字段：

| 键 | 实际含义 | 示例值 |
| --- | --- | --- |
| `name`、`role`、`address` | 名称、角色描述、用户称呼 | `小白狐`、一段角色描述、`你` |
| `traits` | 用 JSON 字符串数组替换整组特征 | `["聪明","温柔"]` |
| `intensity` | 总体角色力度 | `3` |
| `tone` | 语气描述 | `傲娇但友善，做事清楚直接` |
| `warmth`、`tsundere`、`humor`、`emoji` | 对应表达分项力度 | `0` 到 `5` |
| `verbosity`、`language` | 回复详略与默认语言 | `normal`、`zh-CN` |
| `task-persona` | 任务反馈的角色力度 | `1` |
| `model`、`effort` | 新会话模型和强度 | 实际可用标识；`inherit` 表示 null |
| `workspace` | 默认目录模式 | `inbox` 或 `project:<稳定项目键>`，原子更新关联字段 |

字符串取键后的完整剩余内容，允许空格和多行；`address`/`role`/`tone` 可用 JSON 空字符串 `""` 清空。数值、枚举和 traits 按类型严格解析。无值不是清空，返回用法说明。只接受白名单键，不接受 JSONPath、路径跳转、任意通道名、schemaVersion 或 revision 修改。

只有整条消息以完整保留命令词和合法语法组成时才作为配置操作；命令错误直接说明原因，不转交模型猜测执行。普通聊天、引用内容、文件/网页内容中的命令不执行。自然语言“以后傲娇一点”不自动改永久文件，可影响当前交流或提示显式命令。

重置确认码绑定通道、操作类型与目标修订号，只能一次使用；新修改、超时、服务重启或不同操作使其失效。不重置微信绑定、历史、文件、电脑权限或其他账号。批量配置修改和微信上传 JSON 导入不属于本版范围。

### 5.2 新会话与已有命令

| 命令 | 第二版行为 |
| --- | --- |
| `new` | 读取最新有效配置、解析默认参数，创建本通道空白线程；成功后才切换绑定，原线程保留 |
| `st` | 增加当前线程身份名称、快照修订号、实际模型/强度、是否存在待下次生效配置；任务状态仍来自真实执行 |
| `clear` | 保留原“替换上下文并归档原线程”的兼容行为；替代线程须用最新配置，创建失败不得提前归档 |
| `compact` | 压缩当前上下文，保持当前身份快照和执行配置；不冒充空白会话 |
| `exit` | 返回原有通道主会话，不自动将其升级为最新身份；如是旧会话应明确提示 |
| `model`、`effort` | 查询/修改当前线程参数，不修改通道默认配置；返回信息明确标注“当前会话” |
| `config set model/effort` | 修改“未来新会话默认值”，不隐式改变当前线程 |
| `p`、`s`、`s<n>` | 保持项目/任务导航及账号隔离；进入旧线程继续使用该线程自己的快照或旧版状态 |
| `stop`、审批命令 | 保留现有账号/回合范围和实际授权，不受角色描述改变 |

本版不新增“永久删除全部记忆”命令，也不把 `new` 包装成清除所有 Codex 记忆。当前有执行任务时，`new`/`clear` 不静默中断，提示先等待结束或显式 `stop`；配置查看和保存仍可使用。

## 6. 配置保存与会话流程

### 6.1 保存和生效

默认规则：保存后，下次 `new`/`clear` 创建的线程生效。当前线程继续使用自己的快照；改变模型的当前会话命令作为既有例外单独记录，不改变通道默认值。

保存流程：核验当前通道 → 读取最新修订 → 完整校验拟变更对象 → 必要的模型/项目验证 → 原子保存及修订提交 → 回复变更摘要和“发送 new 生效”。失败时保留上一份有效配置，不输出“保存成功”。

新会话流程：

1. 校验通道、是否有运行中任务，以及配置文件是否有效。
2. 固定候选修订及完整配置内容，解析当前可用模型、强度和目录。
3. 将角色与表达编译为该线程的原生开发者指令，使用 Codex 原生接口创建线程并设置执行参数。
4. 核验返回结果，持久化线程归属和配置快照，成功后才切换当前微信绑定。
5. 清楚返回新会话状态，例如“新会话已开始。身份：小白狐；配置：第 3 版；模型：实际模型名；强度：实际强度；未带入上一会话消息。”

参数仅包含本次新线程所需内容；不改全局 Codex 配置、全局 AGENTS 或其他通道。身份指令不能作为虚构的系统消息混进用户正文。原生指令的设置、持久化与恢复能力必须在实施前置验证中确认。

### 6.2 新会话能忘记什么

不主动复制原线程消息、摘要和待处理输入。保留通道身份配置、新线程选定的工作目录及该目录原本适用的 Codex 项目规则。原历史仍存在；Codex 的其他原生记忆机制如有启用，不能因新建线程就声称已清除。未加入长期记忆功能前，不自动把前一个线程的情绪或个人细节写进下一线程配置。

### 6.3 手动编辑与并发

- `config set` 在当前通道配置锁内按最新修订修改；外部编辑与微信写入冲突时拒绝覆盖并提示重新读取。
- 手工编辑保留当前 revision，`reload` 校验成功后由服务递增修订；不能手工提高/降低 revision 冒充已提交版本。
- 每次 `new` 检查文件是否被外部编辑；有效变更经同一保存流程接纳，无效变更阻止新建，不悄悄回退并假装采用新配置。
- 保存采用临时文件、文件刷新、同目录替换及上一有效版本备份。文件与 SQLite 不属于一个原子事务：用提交意图、配置哈希和修订状态对账，恢复时不能仅凭时间戳判断成功。
- 崩溃后文件哈希与已准备提交一致时完成修订；仍是旧文件时撤销未完成意图；出现第三种内容时报告冲突，保留旧有效快照并阻止含糊的新建。
- 损坏配置不停止现有线程或另一个微信通道；支持用户本地修复后 reload，或显式确认 reset。未知版本不自动覆盖为默认模板。

## 7. 通道与数据结构调整

继续复用现有 AccountStore、单宿主、账号范围状态、共用 Guard 和线程归属机制，不新建第二个控制本电脑的实例。

| 结构 | 新增职责 |
| --- | --- |
| 通道运行上下文 | 关联配置读取器、当前有效修订、配置命令处理器及会话工厂 |
| ProfileStore | 文件读写、类型校验、修订、哈希、备份、通道内并发及恢复；不存 token |
| PersonaCompiler | 把经校验的身份/表达编译为原生线程指令，统一实现任务表达优先级 |
| SessionFactory | 解析默认参数、固定配置版本、创建/核验线程、保存快照、最后切换绑定 |
| 控制命令解析 | 增加 config 白名单语法，与普通消息和既有当前会话命令区分 |
| 状态展示 | 区分“通道保存配置”“当前会话快照”“当前线程实际执行值” |

规划新增或扩展的持久化记录（名称在实现时统一，语义不可省略）：

- `channel_profile_revisions`：通道键、修订号、schemaVersion、规范化配置快照、内容哈希、保存时间。
- `profile_change_intents`：通道、预期旧修订、候选新修订、候选内容哈希、准备/完成状态；用于文件与数据库恢复。
- `thread_profiles`：threadId、通道键、配置修订、PersonaCompiler 版本、角色指令哈希、已解析模型/强度/目录、创建时配置快照、legacy 标记。
- 当前线程模型/强度被显式修改时，保持创建快照不变，另记录变更来源；`st` 读取 Codex 实际值，不把旧快照当当前事实。

文件是用户可编辑的配置入口，修订表保存已确认版本；运行线程以创建时快照和 Codex 实际状态为准。配置快照是偏好与指令记录，不是另一套权限事实源。状态与交付仍使用当前 SQLite 原子事务和账号隔离，不拆散现有任务去重/租约机制。

## 8. 旧版本迁移与异常行为

| 情况 | 处理要求 |
| --- | --- |
| 已有 primary/secondary 首次升级 | 在不改变绑定、历史、线程归属和当前权限的前提下，为各通道生成中性默认配置；执行参数默认继承 |
| 原通道已有人设聊天 | 不从历史或本机其他规则文件自动推断永久身份；由用户显式配置 |
| 旧线程没有快照 | 标记 legacy，不追写当前配置；可继续使用，提示 new 可启用身份配置 |
| 恢复新线程 | 使用原快照和原生持久化设置，不按最新通道配置覆盖 |
| 创建结果未知 | 保留原绑定，标明创建结果未知并按已持久化意图对账；不盲目重试创建多个线程 |
| 参数应用失败 | 不切换绑定，不宣称已按配置开始；处理已创建空线程的可见状态，不删除用户已有历史 |
| 通道配置与线程归属不匹配 | 拒绝应用，留下脱敏错误，不能回退到其他通道身份 |
| config reset 后再次进入旧线程 | 旧线程仍沿用原快照，不把重置解释为修改历史 |

## 9. 实施阶段与交付物

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 接口验证 | 用隔离测试线程确认原生身份指令、指定模型/强度、恢复后持久化、Desktop 展示；核实真实返回字段 | 明确可用接口和失败行为，有证据后再进入实现，不用普通用户消息伪装高优先级角色配置 |
| P1 配置基础 | JSON 结构/模板/校验、默认值、私有目录、修订和崩溃恢复 | 无效配置不生效，双通道互不影响，旧数据保留 |
| P2 微信命令 | config 查看/设置/reload/reset、模型和项目选项、帮助与错误提示 | 命令确定性解析，永久配置不会被普通聊天或工具输出改写 |
| P3 会话集成 | SessionFactory、PersonaCompiler、快照、new/clear/st、legacy 兼容 | 新线程使用最新配置，旧线程不被改写，未知结果不重复创建 |
| P4 对话体验 | 闲聊/任务/混合场景、力度映射、自然称呼、授权历史检索与浏览器查证、任务表达约束 | 能自然聊天，信息不足时先获取依据再回复，能实际执行任务，不靠固定前后缀制造人设 |
| P5 回归与用户验收 | 自动化、真实双微信、文件回传、服务恢复及使用说明 | 满足下一节全部必选项，用户确认体验后才标为第二版完成 |

实施前不预置真实用户的身份配置，不为验证重启 Windows。需要刷新 Bridge 时在空闲条件下安排；扫码仅在新增或恢复授权确有需要时由用户完成。

## 10. 验收清单

### 10.1 自动化必选

- JSON 缺失字段、类型、未知字段、Unicode 长度、64 KiB 文件上限、revision 冲突和未知 schemaVersion。
- 写入中断、原子替换、文件/数据库不一致及恢复；失败保留已确认版本，不输出虚假成功。
- 通道 A/B 同时改配置，无法越权读写另一通道文件/快照；确认码不能跨通道或重复使用。
- 模型不可用、强度不兼容、项目消失、选项接口失败时的明确行为，无静默参数替换。
- new/clear 成功后切换、失败保持原绑定、旧会话 legacy、配置更新不回灌历史、compact 不改变身份。
- 普通聊天、语音转写、引用内容、文件和网页中的配置指令不能变成永久写操作。
- 信息不足的对话场景覆盖历史检索归属、浏览器/搜索调用、来源引用、检索无结果及工具不可用；自动化验证流程和边界，不把模拟搜索当作真实事实核验。
- 保持长正文完整交付、链接文件真实附件、双微信路由、Guard、取消、审批和恢复等既有回归检查。

### 10.2 拟人化体验必选，由用户参与判断

为两个测试通道设置明显不同的身份。每组至少连续交流 5 轮，比较强度 0、3、5，以及任务角色力度 0/1/2：

1. 日常问候、分享近况、表达疲惫、轻松玩笑、讨论观点，能自然衔接，不机械重复口头禅。
2. 配置的名称、称呼、特征和语气稳定可感知；力度升高确有差异，而不是仅增加 emoji 或套固定开头。
3. 温柔/傲娇可以表现出来，但不会攻击、敷衍用户或以角色设定拒绝正常工作。
4. 用户说“这次直接给结果”时能降低表演程度；该要求不会自动改永久配置。
5. 在聊天中转为查找文件/生成文档等无风险任务，实际完成并交付；状态、错误、审批仍清楚准确。
6. 任务结束后继续聊天，身份不突然丢失，也不每条消息都再次自我介绍。
7. 提出需要补充历史背景或外部知识的问题，助手会主动查授权历史、使用浏览器搜索核实，并据此回答；查证后仍有缺口时能具体说明，不空泛敷衍，也不虚构已完成的检索。

以上是可观测的产品验收场景，不宣称模型每次生成措辞完全一致；不合格时调整编译策略并重新验收，不能仅靠配置文件存在就算通过。

### 10.3 实机流程必选

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| V2-01 | 两微信分别设置身份和默认模型/强度 | 配置独立、反馈明确，不改全局设置 |
| V2-02 | 保存后继续原会话，再 new | 原线程保持；新线程使用新配置，Desktop 历史可见 |
| V2-03 | 新会话询问上一线程的测试标记 | 中间件未自动复制旧消息；不谎称所有系统记忆已删除 |
| V2-04 | 当前会话 model/effort 与 config set 分别操作 | 能区分当前实际值和未来默认值，互不误改 |
| V2-05 | 闲聊、工具任务、文件回传和失败任务 | 角色自然，实际行为与反馈一致，文件完整可打开 |
| V2-06 | 手动编辑、reload、错误文件、reset | 正确变更下次生效，错误可恢复，重置不删除绑定/历史 |
| V2-07 | 进入旧线程、退出回主线程、空闲重启 Bridge | 快照和 legacy 语义一致，身份不串台，未重复执行任务 |
| V2-08 | 任务运行时修改配置及发新会话命令 | 当前任务不被隐式中断，配置可保存，切换规则与提示一致 |
| V2-09 | 日常聊天中提及既有背景、陌生知识或需核实的观点 | 实际查询本通道授权历史及必要的浏览器来源，回答与依据相符；另一通道历史不泄露，必要时提供来源，工具不可用时如实说明 |

## 11. 发布完成条件

P0 接口能力验证通过；配置、命令、会话快照和对话体验均完成；自动化回归通过；用户确认拟人化聊天和电脑任务两类体验；文档明确可用命令、生效规则、数据边界与遗留限制。

不得将开发完成等同于第二版验收完成。实现、验收、提交推送是分别记录的动作；本需求计划本身不触发运行配置修改或发布。
