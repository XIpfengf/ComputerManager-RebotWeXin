# 多微信实现与用户验收

日期：2026-10-17。基于 [研究](multi-wechat-research.md) 实现；当前版本为V1.0.0。Windows 未重启。微信端实际验证由用户执行，用户已明确确认目前实际使用功能通过，并授权提交推送。

## 实现结构

- 保留一个 Windows 宿主、一个登录启动任务、一个 Codex App Server 和一个 Hook 接收器。
- 原绑定保留为 `primary`，旧状态表和历史线程不迁移、不清空；新账号用 `accounts add <别名>` 追加。
- 单个 SQLite 文件内维护账号登记、线程归属和各账号的状态表命名空间，账号 schema 版本分别保存。原主账号 schema 仍沿用上游版本。所有账号共享原有 `turn_leases`，任务入队、去重责任转移和租约释放仍使用同一数据库事务。
- 状态层只重写内部表/索引/触发器标识；SQL 引号内的文字和绑定参数保持原值。新增上游迁移时必须回归命名空间测试。
- 新账号媒体和 Inbox 使用 `accounts/<别名>/` 子目录，但不使用独立数据库，避免破坏上游的原子入队检查。
- 每个账号创建独立 BridgeDaemon、轮询/退避及状态上下文；宿主热加载新登记的账号。连接失效按账号退避，其他账号继续轮询。
- Codex 门面按线程归属过滤历史和事件，并核验读取、恢复、取消、改模型等操作；审批回调只交给实际收到该请求的账号。
- 线程归属和新账号状态持久化。原有未登记历史/普通 Desktop 线程默认归 primary，新账号创建的线程归对应别名；不自动跨账号分享。
- Hook 根据统一线程登记识别新增账号线程，沿用原 Guard 数据库及冲突拦截。Hook 命令和 manifest 未更换，也未绕过信任。
- 当前不提供第二账号的移除/原地重新登录管理，不承诺任意任务对共享文件的冲突防护；这些属于后续工作。

## 自动化结果

类型检查通过；构建后全量测试 524 项通过，0 失败、0 跳过，其中 6 项新增测试覆盖：

1. 添加账号不替换原凭据与主线程，拒绝重名、重复微信身份、路径穿越和线程抢占。
2. 共享租约按线程归属隔离，另一账号不能读取/释放/对账自己的租约。
3. SQL 字面量、外键、独立 schema 版本，以及同一数据库中状态与租约的事务回滚。
4. Codex 历史列表、线程变更、事件和审批回调的账号隔离。
5. 新增账号线程在实际 Hook 脚本中被识别并阻止 Desktop/Bridge 冲突。
6. 两个真实 BridgeDaemon 共享测试执行器，使用相同消息编号分别启动任务；第三身份被忽略，取消只影响指定账号，回复 token/context 不串用，单个连接失败不阻塞另一账号，重启不重放已执行输入。

上述测试使用模拟微信接口、测试执行器和隔离数据库，不能作为双微信实机收发验收。本机测试日志和升级前一致性备份保存在 `.local/`，不纳入 Git。

## 部署状态

已在无活动租约和排队时仅重启 Bridge，重新由原计划任务拉起。用户已完成第二微信扫码，账号登记成功，primary 与 secondary 均显示 running，仍为同一个 Bridge 进程。两套主线程 ID 不同，第二线程归属 secondary；原绑定身份摘要与原主线程 ID 对比一致，SQLite quick_check 为 ok。随后用户根据实际使用确认功能通过。该结论是整体使用反馈，不视为下列所有故障、审批及媒体边界均有逐项实机记录。

## 用户验收步骤

用第二个微信完成二维码授权后：

1. 两边分别发送不同标记，例如“记住当前标记 A_ONLY”和“记住当前标记 B_ONLY”，再分别询问标记。应各自回复自己的内容，在 Desktop 可看到不同会话。
2. 两边各发 `st`、`s`。当前会话、列表编号互不替换，第二账号看不到主账号历史。
3. A 发一个等待任务，B 发送普通问答；B 的 `stop` 只作用于 B。再由 A 停止自己的任务。不要用真实重要文件做冲突测试。
4. 两边分别发送无隐私小附件，要求读取内容或回传；确认各自只收到自己的文件。
5. 在独立测试任务中验证权限允许/拒绝；禁止用另一微信审批同一短码，审批只影响来源任务。
6. 两边均空闲时可安排 Bridge 重启，再重复收发。断线/登录失效与运行中恢复另行验证，不需要重启 Windows。

当前状态为“自动化通过，用户确认双微信实际使用功能通过”；未单独留证的断线恢复、审批/媒体边界仍作为后续专项验证。账号输入影响的是部署该宿主的同一台电脑，两个微信不会自动变成两个执行设备。
