# 跨会话进度查询与中断诊断

## 问题与已确认原因

2026-10-18 的微信反馈包含两类问题：询问其他 Codex 会话的进度时，语音转写中的“绘画”被直接理解为画图；多次查询中断后，只收到“任务已中断，请重试”的通用提示，无法判断中断的是查询还是目标任务。

对照本机回合记录，查询回合中存在未返回结果的工具调用；下一轮 Codex 日志出现 `Custom tool call output is missing`。这是工具结果缺失的证据，不能单凭它断言网络故障、用户主动取消或目标业务任务失败。

已在独立、无执行任务的 App Server 进程中复现关键故障：对一个超过 500 MB 原始记录的真实目标会话调用 `thread/read(includeTurns=true)`，收到不符合 JSON 协议的输出。旧中间件在解析失败后关闭共享连接，可能影响该连接承载的其他微信回合。旧历史工具先完整读取所有回合、工具输出和图片，再裁剪最后 20 条文字，因而无法提前规避这个问题。

这确认了一条可复现的故障链，不代表已证明每一次历史中断都由同一原因造成。旧服务未保留足以逐次归因的连接终止信息；目标项目自己的备份超时、脚本错误等，也必须与本轮查询故障分别核实。

## 修复后的行为

- 历史工具只向 App Server 请求会话元数据，使用 `includeTurns=false`；不恢复、不执行、不打断目标会话。
- 从元数据提供的原生记录文件只读最多 4 MiB，提取最多 20 条用户/助手文字。跳过工具输出、图片、超大记录、格式异常或未写完的末条记录；不把整份历史送进共享连接。
- 单条文字和总输出设有摘要大小限制。这只限制历史检索的窗口，不改变微信最终长回复完整分片发送的规则，也不删除或修改原生历史。
- 工具保留 `threadId`、`query`、`archived`、`cursor`，新增整数 `beforeBytes`。会话列表用 `cursor` 翻页；记录返回 `window.nextBeforeBytes` 时，将其作为 `beforeBytes` 继续向前检索。`query` 只匹配当前窗口，无匹配不等于整个历史不存在。
- 保留账号归属检查。主通道沿用读取本机未分配桌面会话的权限；其他微信通道不能借此读取不属于自己的会话。
- 输出历史事件时间、观察时间及原生状态。`task_started` 是历史记录；`notLoaded` 只说明当前 App Server 未加载该会话，不能据此推断目标任务仍在执行或已经停止。
- 微信会话恢复时注入通用任务查询约定：结合上下文消歧，先检索与分页，再说明已核实的进度、记录时间及未知项。不改用户人设配置或原有身份快照。

## 22:03 复发：后台入口遗漏与补修

下午的修复只处理了 `channel_history` 工具，没有覆盖后台 Stop 通知对账、通知补发和会话恢复。这是修复范围与验收场景的遗漏。

现场事实：服务主进程自 15:52 持续运行；22:03:14 的微信请求已被接收并启动 Codex 回合，约 3 秒后回合中断。数据库中存在 45 条待对账 Stop 事件，其中目标项目的一条记录发生于 22:02:55。旧后台会轮询这些事件，并通过同一执行连接完整读取历史。3 秒中断不是默认 20 秒 RPC 超时，也不是服务在收到消息时才启动；没有证据归因于离线太久。旧日志未记录具体失败 RPC，不能声称已逐条追溯所有历史故障，但该后台路径已复现相同的连接破坏和无关回合中断。

补修内容：

- 在公共 `CodexRuntime.readThread` 层统一取消原生 `includeTurns=true` 全历史读取。所有需要回合的调用，改为元数据加 `thread/turns/list`，按每页 50 个回合、升序、`itemsView=summary` 遍历；检查游标异常，读取失败不伪装成空历史。
- 原生 summary 页保留用户与最终回复文字，避开中间工具和图片数据。实机比较微信会话中可比较的最终消息，文字一致；回归测试覆盖跨页和长篇最终回复，不裁剪最终交付内容。
- `thread/resume` 使用 `excludeTurns=true`，避免恢复动作隐式返回全量历史。当前部署已核验这些接口；不回退到会破坏连接的旧全量读取。旧 Codex 缺少分页接口时应明确报接口不支持，不能当作空历史或执行成功。
- 单个中间件服务保留一条执行连接，另设只读观察连接。后台 Stop 对账、通知补发和归档活动读取走观察连接；账号归属检查继续生效。后台观察连接不负责发起或重复执行用户任务，其异常不能关闭执行连接。这不是第二个微信中间件服务。
- 增加脱敏的连接诊断日志：时间、执行/观察角色、故障分类、待处理 RPC 方法和异常行长度。不会记录原始协议正文、令牌或聊天内容，也不把协议错误笼统解释成网络超时。

新增的调用链回归先复现“后台查询异常导致无关微信回合被打断”，再验证故障隔离后执行连接保持可用，异常通知仍保留待对账，不自动重做业务任务。真实目标会话通过新公共读取路径返回 7 个回合、约 12 KB，核对到 22:02 那轮已完成；随后读取微信会话成功，无协议诊断异常。

## 失败提示

共享连接意外终止时，中间件为受影响的已知活动回合保留有限的原因分类：协议格式异常或连接断开。不会将原始协议内容、工具输出或上游错误正文直接发给微信。终态对账仍沿用原有流程，不因为连接断开就直接认定远端任务终止。

已确认协议异常时，提示本轮微信请求因 Codex 返回的数据格式异常而中断，并明确“不代表你查询的目标任务已停止”。没有可靠原因时，明确“Codex 未提供明确中断原因”。不自动重新执行中断的任务，避免重复修改文件、发送消息或执行其他有副作用的操作。

用户可以继续说“查一下刚才那个会话的当前状态”，无须为了查询状态重新执行原业务任务。具体业务故障仍需读取对应项目的执行证据，不能把旧截图或旧进度当作实时结果。
