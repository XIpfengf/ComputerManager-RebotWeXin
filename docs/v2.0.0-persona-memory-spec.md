# V2.0.0 Spec：通道长期记忆与人格表达增强

规格编号：V2-PERSONA-MEMORY。修订：1。日期：2026-10-28（Asia/Shanghai）。

状态：`ready-for-agent`。需求及主测试边界已由用户确认；实现与实机验收尚未开始。按用户要求仅在本地保存，不创建远端任务单。本规格是本功能的实现及验收依据，前期调研用于解释候选方案，不覆盖本规格的约束。

## 问题陈述（Problem Statement）

用户已经能够为不同微信通道设置独立的角色、人设、身份背景、称呼和表达强度，并在一个通道下使用多个会话。当前这些设置可以稳定角色身份，但旧交流主要依赖按需历史查询，尚不能持续沉淀通道内的用户偏好、约定和重要事件，也缺少利用这些记忆自然接话的完整机制。

用户希望同一个角色在日常琐事、情绪表达、善意玩笑和观点矛盾中表现得自然、连贯、有自己的表达风格；跨会话仍能记得本通道内发生的交流。角色在执行电脑任务时仍须准确、可靠。

长期记忆若吸收其他通道、外部会话或外部资料，会使角色误认经历、混淆用户和污染偏好。另一方面，重新建立一套人格并替换现有配置，会丢失用户已经维护的角色资料和会话身份契约。这两类回归必须在设计层面排除。

## 解决方案（Solution）

在现有身份配置和会话快照之上，增加以微信通道为边界的长期记忆与动态表达能力。一个微信用户对应一个独立通道，通道内多个会话共同贡献和使用该通道的长期记忆；“多个会话”指现有会话集合，不引入父子 Agent 或第二个执行器。

读取权限和记忆归属是两个不同判断：现有授权能力可以读取外部会话，但被读取的内容只作为本次参考，不能写入本通道长期记忆、画像、相处习惯或人格成长材料。内容被本通道助手转述后仍保留外部来源属性，不能因出现在本地会话中而洗成自身经历。

角色身份及背景继续来自现有人设；记忆帮助角色理解“与你聊过什么、你明确偏好什么”，表达增强帮助角色在恰当场景自然回应。用户能查看、纠正、忘记或关闭记忆；任务执行、权限、审批和交付沿用现有可靠链路。

## 用户故事（User Stories）

1. 作为微信用户，我希望长期记忆属于自己的独立通道，以便不会与其他微信用户混淆。
2. 作为微信用户，我希望通道内多个会话共同积累长期记忆，以便换会话后仍能延续交流。
3. 作为微信用户，我希望通道主会话和其他归属会话使用同一记忆边界，以便不产生彼此割裂的人物关系。
4. 作为微信用户，我希望会话当前选择与历史归属分开判定，以便导航到一个任务不等于把它的历史据为己有。
5. 作为微信用户，我希望经授权读取外部会话仍然可用，以便助手可以查进度和参考资料。
6. 作为微信用户，我希望外部读取结果不能成为我的长期记忆，以便助手不会把别人说过的话当成我说的。
7. 作为微信用户，我希望外部内容被总结或转述后仍不得入库，以便不会通过间接引用污染画像。
8. 作为微信用户，我希望外部会话中的角色和用户身份不被继承，以便本通道角色保持自己的身份。
9. 作为微信用户，我希望来源不明的历史默认不自动入库，以便系统宁可少记也不错误认领经历。
10. 作为微信用户，我希望现有名称、角色、身份背景和称呼完整保留，以便已有配置继续有效。
11. 作为微信用户，我希望现有亲和、傲娇、幽默、表情和详略设置继续控制表达，以便不必重新调教角色。
12. 作为微信用户，我希望旧会话保持创建时的身份快照，以便新版能力不会偷偷改变旧角色。
13. 作为微信用户，我希望修改通道配置后仍按现有规则作用于新会话，以便生效时机可预测。
14. 作为微信用户，我希望长期记忆与角色身份分别管理，以便记住一件事不会改写角色背景。
15. 作为微信用户，我希望角色能记住我明确表达的稳定偏好，以便不用反复说明。
16. 作为微信用户，我希望角色能记住通道内重要约定、决定和事件，以便交流连贯。
17. 作为微信用户，我希望短期疲惫或一次玩笑不被永久定义成性格，以便画像不会失真。
18. 作为微信用户，我希望系统区分我的喜好与角色自己的喜好，以便主体不会混淆。
19. 作为微信用户，我希望记忆保留发生时间和原话出处，以便需要时核实依据。
20. 作为微信用户，我希望新的明确纠正优先于旧偏好，以便角色跟得上实际变化。

22. 作为微信用户，我希望开启长期记忆后新会话可使用相关旧记忆，以便空白会话不等于重新认识我。

34. 作为微信用户，我希望善意调侃能得到符合角色的俏皮回应，以便角色具有辨识度。
35. 作为微信用户，我希望自己受挫时先得到合适的回应，以便不用立即接受长篇建议。
36. 作为微信用户，我希望角色在观点冲突时温和而明确地说明判断，以便获得有价值的交流。
37. 作为微信用户，我希望昵称、动作文字和口头禅适量变化，以便不会每句都重复同一种表演。
38. 作为微信用户，我希望提出“直接给结果”后本轮表达能收敛，以便不被角色演绎妨碍工作。
39. 作为微信用户，我希望从聊天转为电脑任务时仍是同一个角色，以便身份连续且任务清楚。
40. 作为微信用户，我希望任务失败、审批和限制如实说明，以便角色语气不会掩盖事实。
41. 作为微信用户，我希望记忆提炼在后台进行，以便不会明显阻塞每条回复。
42. 作为微信用户，我希望记忆服务失败时普通交流和电脑任务仍能继续，以便扩展故障不拖垮现有能力。
43. 作为微信用户，我希望重连、排队和交付重试不会重复写入记忆，以便系统长期使用后不会膨胀或自我强化。
44. 作为微信用户，我希望跨会话并发修改不会覆盖已确认事实，以便多个会话都可安全使用。
45. 作为微信用户，我希望升级后原绑定、权限、当前会话和归档策略不变，以便日常使用不受打扰。
46. 作为维护者，我希望能观察记忆任务进度、失败和上下文预算，以便定位问题且不输出私密对话。
47. 作为维护者，我希望先用合成数据验证再进行授权实机体验，以便不把模拟结果当成真实效果。
48. 作为维护者，我希望 v2 功能在独立 worktree 和分支推进，以便 develop 继续修复日常问题。

## 实现决策（Implementation Decisions）

### 1. 领域与归属

- **通道**是一个已认证微信用户的独立运行上下文，持有自己的身份配置、会话归属和长期记忆。**会话**是现有 Codex 持久化会话，同一通道下可有多个会话；不是父子 Agent 结构。
- 长期记忆的命名空间为通道，来源坐标细化至会话、回合及消息。通道身份由认证上下文取得，不能由模型或用户传入的任意别名决定。
- 采集、历史回填、提炼提交、检索、注入、查看、修改和导出均核实通道归属。会话绑定或可见性不等于历史归属。未归属、归属冲突或无法核实的会话不自动吸收。
- 归档不改变合法归属；开启历史回填时可包含本通道归档会话。禁止重认领旧历史来转移记忆；运行中发现归属变化时停止相关作业并隔离派生条目，未经核对不得继续注入。

### 2. 外部参考与自身记忆严格分开

- 不扩大已有跨通道或 Desktop 读取权限；继续使用现有授权与只读查询机制。本规格不放宽 `channel_history` 的本通道边界。
- 引入来源类别及传播规则：本通道原始交流、外部参考、混合来源、来源未知。外部会话、其他通道、委派回传、网页、附件和工具返回默认属于参考材料，不能以这些材料直接或间接建立个人记忆。
- 外部材料经过摘要、复述、翻译、回传或画像编译后仍保持该类别。处于本通道回合中不是合格来源的充分条件；不能直接把全部助手最终文本送入记忆抽取。
- 来源在数据管道中结构化传递，不只依赖提示词或模型自报。混合内容无法可靠拆分时，不自动提炼该部分；宁可不生成事实也不把它标成本通道经历。
- 本通道用户自己的明确决定可以成为新记忆，例如看过外部建议后明确说“以后给我的回复简短一点”；保存的是这次本地决定及原话，不是导入外部用户画像或把外部事件改称亲身经历。引用粘贴本身不算本人的明确陈述，不能作为迁移外部记忆的后门。
- 可记住“本通道用户曾要求查询某项外部任务”这一原始交互事实，但不吸收查询返回的外部进度、身份或经历；任务进度仍由实时查询核实，不能由旧记忆背书。

### 3. 人设增强与兼容

- 继续以 ChannelProfile、PersonaCompiler、ProfileStore、ChannelProfileService 及会话身份快照为身份事实源；名称、角色定位、背景文字、称呼、特征、语气和强度设置不废弃、不替换。
- 稳定身份、动态通道记忆和短期互动状态分别编排。自动提炼不得修改身份配置、会话身份快照、默认模型、全局规则或权限。
- 原有 `config`、新会话、替换会话、压缩和返回主会话的语义保持；配置修改仍只影响未来新会话，旧会话及 legacy 状态不追写新身份。动态记忆启用不等于给旧会话注入最新人设。
- 用户纠正可形成带证据的记忆或表达偏好候选，但不能自动改永久人设。需要修改角色时继续走现有明确配置流程。

### 4. 采集、存储与提炼

- 复用 AccountStore 和账号范围运行机制，不建立第二个 Bridge 或另一个聊天历史真源。原始会话历史仍由现有执行环境持久化，记忆保存必要的事实、证据坐标与派生关系。
- 记忆数据至少表达：通道、主体、类别、正文、来源、证据类型、候选/有效/冲突/已取代状态、有效时间、修订和派生关系。模型置信度不能代替服务端来源校验。
- 只提炼允许的通道内原始交流；记忆注入片段、工具结果和助手已有记忆的复述不再次作为新证据。角色自述不得抽成用户偏好。
- 稳定偏好、重要约定、决定与事件按主体和时间处理；临时情绪、玩笑、猜测和角色动作不自动固化。凭据、令牌等内容不自动进入普通画像。
- 后台作业记录增量游标、批次和幂等键，遵循账号内串行提交、失败退避、调用预算和超时。未知调用结果先对账，不能无限重试或覆盖已确认内容。提炼模型没有执行工具或修改人设的权限。
- 使用既有 SQLite 和私有运行区扩展持久化；具体表布局在实现时确定，不能削弱账号边界、来源校验、事务与恢复行为。

### 5. 检索、注入与自然表达

- 根据本轮语境检索本通道相关事实，考虑明确程度、相关性、时间及新纠正；摘要画像由有效事实重建，不取代原始证据。
- 首版采用可验证的本地检索，验证中文同义表达和分词行为；不预设必须部署向量库或额外服务。
- 人格作为稳定身份指导，记忆作为低信任参考，短期状态按本轮变化。动态记忆承载方式必须先验证，避免修改用户原文、覆盖旧身份、泄露内部标记或每轮累计全量上下文。
- 生成前确定本轮使用的记忆修订及预算；排队消息在实际执行时读取合适的记忆快照，交付重试复用已经生成的回复。立即执行与排队执行遵循同一来源和预算规则。
- 在现有表达等级上增加行为原则与少量场景示例：闲聊自然接话，受挫先回应，玩笑适度嘴硬，分歧有依据地表达，工作时精确简洁。动作文字可选且克制，不每句自报角色或堆砌口癖。
- 首版优先在同一生成链路中融合人格和记忆，不新增自由改写任务结果的第二模型。错误、数值、否定、权限、路径、代码、附件和完成状态不得为表达效果改变。
- 不将没有记录的关心、经历或执行动作写成事实。无相关记忆或检索故障时如实说明，不假装记得。

### 6. 用户控制与生命周期

- 记忆默认按通道独立关闭，升级不偷偷采集旧历史；用户显式开启后才启用常规采集与相关记忆注入。历史回填另行确认范围，不能因启用未来记忆而扫描全部旧记录。
- 提供查看、来源追溯、纠正、忘记、暂停/关闭、导出、回填预览与进度控制。管理入口采用现有确定性控制机制，具体命令名在实现前固化到帮助及测试，不允许模型直接用任意文本改库。
- 开启后，正常新会话可读取同通道记忆但不复制旧会话全文。无记忆临时会话同时关闭记忆读取、写入和后续回填，显式选择恢复前不补采其交流。
- 忘记操作对条目及派生画像、检索缓存和后台待提交结果一并生效，写入删除墓碑或等效排除记录。旧批次提交前重验策略与修订；重扫、重新提炼和同义改写不能自动恢复被忘记内容。
- 关闭后停止新增采集、提炼、回填和动态注入，保留已存记忆以便之后显式恢复；重新启用不自动补采关闭期间的内容。切换关闭或临时会话时使待处理写入失效，运行中的模型不能因此把结果继续写库。
- 删除记忆不等于删除原始聊天；已经进入正在使用的会话上下文的信息不能承诺即时抹除。需要彻底避开旧上下文时使用新的无记忆会话，并如实提示这一边界。
- 人设重置不清空记忆，记忆删除或关闭不重置人设。现有会话归档规则、绑定和权限不被记忆策略改变。

### 7. 历史、运维和开发边界

- 历史回填只接受已核实属于本通道的会话；从现有记录增量、有界读取，保留完整性标记和游标，不能将单次窗口当全部历史。外部导出或其他通道不在回填入口中。
- 回填不打断运行任务，支持暂停、恢复和预算限制。使用远端提炼模型时，明确所选片段进入模型请求；本地存储不代表提炼离线或零成本。
- 记忆异常不阻塞原有交流、任务、审批、取消与交付；失败与零命中分别报告。可观测信息记录作业状态、计数、修订及预算，不输出私有原文和凭据。
- 在独立 worktree 和功能分支实现，从 develop 的已核验基线开始；原 develop 目录继续日常修复。后续同步 develop 时审查并解决冲突，不自动合并、提交、推送或发布。

## 测试决策（Testing Decisions）

### 已确认的主测试边界

用户确认：以现有 **Bridge 双微信通道集成测试**为主要入口，验证同通道跨会话共享记忆、外部读取及其转述不得入库，以及现有人设快照保留。仅为难以通过该入口可靠模拟的崩溃恢复、删除墓碑和持久化竞态补充存储契约测试。

测试关注用户可观察行为和安全契约，不断言内部调用顺序、私有函数或数据库实现细节。既有先例包括 Profile Bridge 的配置→新会话→更新→旧快照保留流程、多账号的认证/取消/路由隔离，以及有界历史读取和 Outbox 恢复测试。沿用临时数据库、可控执行器、模拟微信交付与可控时钟，不接触真实用户数据。

| AC-05 | 本地原话混有引用、文件内容或外部总结 | 只处理可证明的本地原始陈述；来源不明或不可拆分部分不自动写入 |

| AC-08 | 用户偏好与角色自述、玩笑、临时疲惫并存 | 主体不混淆；临时状态和虚构角色动作不固化为用户事实 |
| AC-09 | 旧偏好、新纠正与相互冲突证据 | 明确新纠正生效；冲突可见，不凭重复次数自动覆盖 |
| AC-10 | 普通新会话与无记忆临时会话 | 前者按策略读取通道记忆，后者不读、不写且不被以后回填 |
| AC-11 | 遗忘后旧批次提交、重扫、同义提炼和缓存命中 | 被忘记条目及派生画像不能复活；不声称原始对话已被删除 |
| AC-12 | 关闭期间有消息、提炼在途、重启后重新开启 | 停止读写和回填；在途结果失效；不开启期间历史不被自动补采 |
| AC-13 | 同一回合重连、取消、排队、未知结果或交付重试 | 记忆提交幂等，来源与通道不变；不因交付重试重新生成或重复计为证据 |
| AC-14 | 两个会话同时写事实或用户同时纠正/删除 | 不丢已确认修改；后台旧修订不得覆盖新纠正和遗忘 |
| AC-15 | 损坏记忆库、提炼超时、预算耗尽、历史窗口不完整 | 原有任务继续；区别故障与零命中；回填可恢复，不称已读完全部历史 |
| AC-16 | 人设或记忆材料含权限、配置、执行指令 | 不能因此提升权限、修改永久人设或执行操作 |
| AC-17 | 文件、长回复、错误状态、审批和取消 | 输出语义及交付完整性保持，不能因拟人化捏造完成或破坏真实附件 |
| AC-18 | 真实双微信的日常交流及聊天转任务 | 用户确认角色自然且一致，不机械复读；两通道有独立背景；实际操作结果可核实 |

### 体验与成本验证

- 自动化验证流程与边界；使用模拟模型时不声称真实模型记忆准确或拟人效果通过。
- 使用相同模型设置，对日常分享、善意调侃、受挫、观点冲突、历史指代和混合任务进行旧版/新版多轮对比，由用户判断接话能力、自然度、人格稳定性与重复程度。
- 在隔离测试通道验证启用、纠正、遗忘、关闭、重连和跨会话；再按用户授权做微信实机体验。保留既有类型检查与相关回归门槛，不为验证擅自重启现有服务。
- 分别测在线回复和后台提炼的调用次数、token、P50/P95 延迟、回填进度与失败退避。固定数字目标在 P0 有数据后记录，不在本规格中虚构性能保证。

## 范围之外（Out of Scope）

- 替换现有人设模型、重建角色身份、自动永久改写人格或修改旧身份快照。
- 以任何方式把其他通道、外部会话、外部导出或工具资料导入为本通道自身记忆。
- 放宽跨通道查询权限、建立操作系统级沙箱、让多个微信变成多台执行电脑。
- 新的 Agent Loop、第二个微信控制服务、替换 Codex 执行器或把 DSH 插件直接安装到当前 Bridge。
- 完整记忆树、关系图谱、多角色商城、自动情感推送、真人克隆、动画或实体姿态、独立语音与表情包平台。
- 自动永久删除原始聊天、抹除已进入模型上下文的信息，或把心理状态推断当成事实。
- 本轮实现代码、部署服务、提交推送、合并 develop 或发布 v2.0.0。

## 补充说明（Further Notes）

- 本规格把“通道内会话是自身记忆唯一来源”和“增强现有角色能力”提升为不可降级的验收契约；任何候选库或接口不满足时应换适配方式，不能放宽需求。
- 实施顺序：P0 动态上下文与无执行工具的提炼接口验证 → P1 通道来源与记忆治理 → P2 增量提炼/有限回填 → P3 自然表达 → P4 回归及用户实机验收。P0 若证实接口无法满足来源隔离或旧快照要求，记录阻碍并调整技术方案，不假定已支持。
- 以 AgentSoul 的分层、澜记忆的表达与画像、器灵的来源和反馈思路为参考；不照搬他人角色或宿主特定 UI。引入实际代码前固定版本并逐项核对许可。
- 本功能的方案文件与后续实现位于仓库内独立 worktree；主目录保持 develop 用于日常修复。当前版本仍为 V1.0.2。
- 跟踪方式按用户明确选择为本地文档；`ready-for-agent` 是本地规格状态，不代表代码已完成、实机已通过或获准发布。

## 2026-11-03 用户批准的表达与情绪增量

本节记录后续明确授权，扩展前文的首轮讨论范围，不改变来源隔离和身份快照契约。用户批准完成记忆召回/回执、场景回复偏好、独立短期情绪及本机控制页，并在验收后更新自启动服务，为两个已绑定微信通道开启。该授权不包括提交、推送、合并、真实历史画像或额外收费模型配置。

- 固定身份保持；表达偏好、短期情绪、用户事实记忆分别管理。application 只携带代码生成的有限表达策略，原始记忆仍为untrusted。
- 记忆先过账号/来源/有效性门，再匹配、时间排序、去重与预算。最早查询可查看被纠正的历史版本，忘记后不经历史召回或旧回执复活。
- 本轮明确的直接/收敛要求优先；任务、失败、取消和审批如实表述。关闭项与0等级不得被情绪或旧偏好重新开启。
- 短期情绪按本通道合格原话事件更新，有限增量、恢复、防抖、幂等，可关闭和重置；不自动改变身份或写成长期用户事实，不使用新增后台Agent/模型循环。
- 本机页仅监听回环，访问与设置按账号固定，修订校验，拒绝跨源及任意账号/身份字段。预览只展示策略；准备与模型接收回执分开记录。
- 先使用合成数据与模拟集成验收，再验证固定构建、自启动、双账号启用及旧资料保留。真人自然度不以自动测试代替。详细命令与实现见 [动态表达与本机控制页](v2.0.0-interaction-guide.md)。

## 2026-11-04 表达姿态需求澄清

用户进一步要求沿参考项目的语境分析与回复组织思路设计：温柔只是可选姿态，依人设与场合容纳直率、善意挑衅、傲娇、嘴硬、保留判断和表达变化；概念及逻辑讲解仍须明确，同时保留放松的幽默和角色语感。中文词语位置、句法、断句与语气应参与回复生成，不能只给成品追加甜话或口头禅。

该方向继续遵守事实/执行准确、通道来源、既有设置与旧身份快照契约，不将变化感扩大成随机人格或不可靠执行。具体模块、后续实施和验收证据见 [中文表达姿态设计](v2.0.0-expression-design.md)。用户随后明确授权先写行为测试、完成验收与回归后更新重启原自启动中间件，为两个微信通道启用并保留原资料，不提交或推送。

后续已完成该增量实现、722 项回归、隔离合成模型核验及双通道固定构建更新。此结果不代表自动提炼、独立人类盲评或长期自然度已通过。
