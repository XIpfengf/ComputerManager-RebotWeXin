# 会话保持与历史生命周期方案

这是当前第二版已实现功能的规则与验证说明。完整部署步骤、人设及基本命令见 [第二版部署与命令手册](v2-user-guide.md)。自动归档默认关闭；永久删除仍不提供。

## 本次生效：持续保持当前会话

微信通道默认持续使用当前会话，取消 30 分钟无活动自动退出。关闭微信、长时间不发消息、电脑休眠以及 Bridge 重启都不应自行切换会话。新消息仍进入持久化保存的线程；服务恢复不等于重做已经完成的任务。

`new` 主动创建并进入新会话；`exit` 主动返回通道原主会话。既有明确操作 `s<n>`、`p<n>` 和 `clear` 保留原语义：选择项目会退出当前会话，`clear` 创建替代会话成功后归档旧线程。原主会话可能仍为旧身份，exit 不自动更新其配置。

后台任务结果仍正常发送，但通知不会夺取会话焦点；通过 `s` / `s<n>` 明确进入目标任务。列表编号有效期、审批确认码和通知投递期限保持各自规则，它们不是聊天历史的寿命。

实现复用 bindings 表的 expires_at_ms，写入最大安全整数作为持续模式的兼容标记，不是延长为某个有限天数。启动时保留数据库中最后一次尚存的选择，包括升级前已超时但未被新路由覆盖的记录；明确 exit 后无绑定记录，不会复活旧选择。已被旧版本覆盖的更早选择无法自动恢复，需用 s<n> 重新进入。当前宿主所有微信均启用持续模式；旧 sessionTimeoutMinutes 字段暂作上游兼容数据，不再控制当前产品的会话退出。

## 已实现：历史归档，默认关闭

此前持续会话改造验证：类型检查、546 项全量测试及 Git 空白检查通过，包含一年无交互、旧超时绑定升级、数据库重开和通知不切换场景。线上通道空闲时已备份状态库并仅重启 Bridge，两微信均 running；绑定凭据、最后选择、主会话、身份配置及全局 Codex 设置保持不变。真实已选择线程在一年后的读取时间仍有效。未重启或注销 Windows，未对真实微信历史执行归档或删除；微信最终体验仍由用户确认。

归档服务和命令现已实现。两个真实微信的自动归档默认关闭；只有用户发送 history enable 才启用。不会删除历史、配置修订或用户文件。

### 建议默认规则

- 自动归档开关按通道设置，默认关闭。用户启用后每天扫描一次，候选为连续 30 天无用户/助手活动的非当前线程。
- 每通道至少保留最近 20 个未归档会话；只处理归属明确的本通道托管线程，不处理其他微信和非托管 Desktop 线程。
- 当前绑定、主会话、用户固定保留的会话，以及有租约、执行任务、队列、审批或待交付结果的线程不参与自动归档。实际执行前再次检查。
- 归档完整保留历史与身份快照，可从归档列表恢复，也能通过授权历史工具检索；归档不改变当前绑定。
- 活动时间不可靠、归属不明确、接口失败或结果未知时跳过并留记录。未知结果先查询确认，不盲目重复操作。

### 数据分层

| 数据 | 建议策略 |
| --- | --- |
| Codex 原始对话及归档会话 | 默认永久保留，不自动删除 |
| 线程身份快照 | 线程保留就保留，归档不丢失身份 |
| 身份配置修订 | 先全部保留；以后只考虑裁减未被线程引用的旧版，当前版和上一有效备份必留 |
| 模型变更审计 | 暂保留，后续另定压缩与导出策略 |
| 收发去重与投递元数据 | 延续现有约 30 天清理，未完成和仍被引用的数据保留 |
| 中间件临时媒体 | 只清理无任务、附件意图或待发送记录引用的受管快照 |
| 用户原文件和任务产物 | 不纳入会话清理，不因归档或超时删除 |

磁盘不足先报告占用及可回收受管缓存，不自动扩大到 Codex 数据库、其他目录或用户文件。不要直接编辑 Codex 私有数据库来删除历史；先验证官方接口与恢复能力。

### 后续交互和执行流程

以下命令作为独立文字消息发送到微信，作用于当前微信通道。语音转写、附件引用、自然语言路由不能进入永久策略命令。

| 命令 | 作用 |
| --- | --- |
| `history help` | 查看帮助 |
| `history policy` | 查看启用状态、30天/最近20条规则和最近扫描时间 |
| `history enable` / `history disable` | 开启或关闭本通道每日自动归档；开启意味着按规则执行，无需每天确认 |
| `history preview` | 只读预览候选与排除理由，不执行归档 |
| `history archive` | 预览并产生两分钟内有效的一次确认码 |
| `history archive confirm <码>` | 再次扫描，只有仍符合条件的本次已预览候选才归档 |
| `history pin <会话ID>` / `history unpin <会话ID>` | 固定保留或取消本通道固定标记 |
| `history restore <会话ID>` | 恢复本通道归档线程，保留身份快照，不切换当前选择 |
| `history reconcile` | 查询原生列表，对账接口结果未知的操作，不盲目重发 |

恢复后用 `s` / `s<n>` 进入，或继续使用既有 `sarc` 查看归档列表。没有删除命令；30天和最近20条目前为固定规则，不支持在 profile.json 中添加未知生命周期字段。

流程为：按通道扫描 → 预览候选与排除理由 → 用户启用或确认 → 逐项复查归属和忙碌状态 → 原生接口归档 → 持久化结果 → 简短汇总。断线恢复应幂等，不创建替代线程，不改当前绑定。普通聊天、网页和历史内容不能修改生命周期设置。

首轮不实现永久删除。未来如确需删除，应另行设计范围、导出备份、预览、一次确认与恢复期限，并取得单独授权；自动归档授权不等于删除授权。

### 实现与验证边界

新模块 `src/history/history-service.ts` 负责明确线程归属、实际消息活动时间、保护条件、每通道串行操作、一次确认和每日扫描。策略、固定标记与操作记录保存在原私有状态库的 history_policies、history_pins、history_operations 表；没有新增第二个宿主，不更改人设 JSON 格式。每次扫描尝试前记录时间，服务重启或网络异常不会形成紧密重试；成功后保存汇总，并通过已有可靠投递通道通知微信。

归属要求 thread_accounts 中明确登记，不能利用旧主账号的默认历史可见性处理非托管 Desktop 会话。实际聊天活动取含用户/助手消息的回合时间，而不是线程改名或恢复时间；无可靠时间或非空闲状态跳过。执行前获取 Guard 租约并复查保护与活动条件，持久化操作意图后才调用原生归档接口；结果未知保留待对账状态并排除于候选。对账明确仍未完成的操作不自动重发，需要重新预览或后续扫描再评估。

当前 App Server 的线程结构不提供 Desktop 固定标记，因此只读查询当前 Codex 的 state_<版本>.sqlite 中 is_pinned，绝不修改该数据库；路径、格式或线程无法核实即停止该次归档。中间件自己的 history pin 另存在私有状态库，两种固定标记都保护会话。

单元/集成测试覆盖默认关闭、30天与最近20条、当前/主/固定/租约/审批/待交付保护、双通道与非托管隔离、一次确认与过期、执行前状态变化、每日扫描及重启、未知结果对账、恢复不切换、语音命令阻断、用户文件保留。真实 Codex 隔离会话验证归档与恢复接口、聊天记录和身份快照保留；这不等于真实经过30天或完成微信界面体验验收。

### 验收入口

用户可先发送 history policy、history preview 核对，确认需要后台归档后再 history enable。当前活跃的林鹤会话不会成为归档候选；新部署不主动归档任何真实历史。永久删除与配置修订裁减仍未实现，须另行明确需求与授权。

本轮交付验证：类型检查、558项全量回归（0失败、0跳过）及隔离真实 Codex 归档/恢复接口验证通过。线上空闲时备份状态库并仅重启 Bridge，两个微信均恢复 running；绑定、当前选择、人设及全局 Codex 配置未变化。两个自动归档开关均为关闭，线上历史操作表为空，未归档或删除真实微信历史。Windows 未重启。微信端可用 history policy 和 history preview 继续核验显示；真实经过30天的每日调度与用户界面体验不作为本轮已完成的实机证明。

真实只读预览另确认了历史线程的 notLoaded 状态：未载入不等于执行中。此类线程仍须具有可靠活动时间、所有消息回合已结束，并通过租约/审批/队列/通知保护检查才有资格归档；不直接把 notLoaded 当成忙碌，也不因此放宽跨进程保护。
