# 完整长回复与文件链接附件交付

日期：2026-10-17。按用户最终要求实现：全文分片、不设回复总条数上限、文件链接转真实附件、调整长任务提示。此前研究中的“极长回复用全文附件替代”方案未采用；正文始终完整分片。

## 改动

- 单条保持保守的 2,000 UTF-8 字节预算。优先在段落、换行或句末拆分，必要时按 Unicode 字符簇切分；不丢弃剩余正文，不添加截断提示。
- 附件和文字不再共享 3 条消息的预算。所有分片一次保存为 Outbox 交付计划；恢复、完成判断、通知回复路由、过期清理均支持任意正整数片号。
- 重放按数字片号排序，避免 1、10、11、2 的字典序错误；一片失败后本组后续片暂停。已确认部分不重发，失败片使用固定 client_id，冷却 30 秒后允许后续轮询再次重试。重新登录失败等仍遵守渠道退避规则。
- 同一回合的并发终态信号共享交付计划；终态发送与后台重放对同一条消息使用单次在途发送，减少并发重复。
- 最终回复里的 Windows 绝对路径、相对文件链接和本机 file URI 会转为经过校验的不可变附件快照，覆盖独立一行及行内 Markdown 链接。普通 HTTP(S) 引用保留；代码块/行内代码不视为附件请求。
- 自动附件只读取当前任务 cwd 内的真实文件，沿用已有目录、链接、硬链接与 100 MB 大小检查。目录外文件需由执行任务先复制进入任务目录；失败会显示原因，不只给手机打不开的本机路径。
- 登记附件与链接附件按快照内容去重；`send_file` 工具本身仍最多登记 2 个，自动链接附件不受此数限制。
- Desktop/已安排任务通知复用相同完整分片和附件准备逻辑；通知携带的正文/附件仍发给所属微信，未取消账号隔离。
- 保留约两分钟后的一次等待提醒，将推测工具/审批/网络故障的文案替换为：“⏳ 任务还在处理中，完成后会自动发给你；可发送 st 查看，或发送 stop 停止。”没有增加虚构进度或额外模型调用。

## 用户验证

- 让机器人生成超过原先三条容量的完整回复，带明确末尾标记，确认最后一段收到且顺序正确。
- 要求在当前任务目录生成几个小文件，并在最终回复中提供文件链接；确认微信实际收到并能打开，不只是显示链接。
- 长回复和文件一起产生，确认文件不挤掉正文；分别在两个微信执行，检查不串消息。
- 用无敏感内容的任务等待超过两分钟，检查提醒文案及最终结果。

## 内部规则引用边界

内部 `SKILL.md`、`AGENTS.md`、`CLAUDE.md` 及 Codex 技能/插件/记忆目录的 Markdown 引用保留名称，不隐式生成附件，也不显示复制到工作区的发送失败提示。普通工作区交付文件仍按原规则转换与校验；用户明确要求交付规则文件时仍须通过授权的 `send_file` 流程，不能借引用绕过边界。该修复包含 standalone、内联、编码路径和 file URI 回归。
